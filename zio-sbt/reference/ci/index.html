ZIO SBT CI

ZioSbtCiPlugin generates the GitHub Actions workflows of a project from its build.sbt, so continuous integration (CI) is configured in one place. The default workflow builds, tests, lints and publishes the project, and every part of it can be changed with sbt settings or replaced by custom jobs. The model of workflows, jobs and steps lives in ZIO SBT GitHub Actions.

To install the plugin, add addSbtPlugin("dev.zio" % "zio-sbt-ci" % "0.8.12") to project/plugins.sbt, as described in Installation. Using SNAPSHOT versions of the plugin also needs resolvers ++= Resolver.sonatypeOssRepos("public").

The plugin declares trigger = allRequirements, so having it on the classpath is enough, and enablePlugins(ZioSbtCiPlugin) is not strictly required. Its settings are defined at ThisBuild level, so set them as ThisBuild / ciSomething := ..., or inside inThisBuild(...).

To use the plugin, install the ZIO Assistant GitHub App on the repository.

Default Jobs​

The generated ci.yml contains these jobs:

JobWhat it does
buildCompiles everything, publishes locally, and builds the website
lintChecks the generated workflow is up to date, then runs sbt lint
testRuns the test suite across the target Java versions
update-readmeRegenerates README.md from docs/index.md and opens a PR
ciAggregate gate: succeeds only if the jobs above did. Point branch protection at this one
releaseRuns sbt ci-release on a published release or a manual run, and on pushes to the default branch for SNAPSHOTs
release-docsPublishes the docs to npm after a successful release, or on a manual run with docs-only set to true
notify-docs-releaseDispatches an update-docs event to zio/zio with the docs package name and version, so the ZIO website picks up the new docs

notify-docs-release takes the docs version from the release tag, or from the newest v tag on a manual docs-only run, and waits for up to five minutes until npm lists exactly that version. It fails if the version never appears. With HashVersioning as ciDocsVersioningScheme, it still reads the latest version with npm view <package> version.

The default workflow runs on workflow_dispatch, published releases, pushes (to ciEnabledBranches when set, otherwise every branch) and pull requests that do not target gh-pages.

Concurrency of the Default Workflow​

By default ciConcurrency is one run per workflow and ref, and an in-progress run is cancelled when a newer run starts in the same group. The group is ${{ github.workflow }}-${{ github.ref == format('refs/heads/{0}', github.event.repository.default_branch) && github.run_id || github.ref }}. On the default branch the group ends with the run id, so every run is kept. On any other ref, including a tag such as refs/tags/v1.9.2, the group ends with the ref.

A release event and the push of its tag have the same ref, so they share one group, and the run that starts later cancels the earlier one. To change this, set ciConcurrency as described in Control CI Concurrency.

Settings​

All settings are ThisBuild-scoped.

Types Used in Settings​

The types that the settings above take, such as Job, Step, Concurrency, DependencyBot and DeployPreviewMode, are described in ZIO SBT GitHub Actions. They live in zio.sbt.githubactions and are not exported through autoImport, so import them explicitly. The reusable steps live in zio.sbt.ZioSbtCiPlugin.

Helper Methods​

targetScalaVersionsFor(projects*) takes a list of projects and returns a Map from each project id to its crossScalaVersions. It is meant for ciTargetScalaVersions, as shown in Test Against Several Scala and Java Versions.
